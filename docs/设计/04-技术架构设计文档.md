## 一、架构设计原则

### 1.1 核心约束

在动手前先明确约束条件，避免技术选型脱离实际：

| 约束 | 内容 | 影响 |
|------|------|------|
| 团队规模 | 1-2 人独立开发 | 不上 K8s、不拆过多服务 |
| 业务特征 | AI 调用为主、突发流量、低频长任务 | 必须异步化、必须限流 |
| 预算 | MVP 期 ≤ 2000 元/月 | 单台云服务器起步 |
| 合规 | 数据境内、不出境 | AI 服务商必须境内 |
| 演进 | 用户增长后再升级 | 不做过度设计 |

### 1.2 设计原则

| 原则 | 含义 |
|------|------|
| 单体优先 | 单体应用起步，模块化拆分准备，但不物理拆分 |
| 异步优先 | AI 类调用一律异步，禁止同步等待 > 3 秒 |
| 降级优先 | 任何外部依赖必须有降级方案 |
| 可观测性优先 | 关键路径必须有日志、监控、链路追踪 |
| 成本可解释 | 每次 AI 调用能算出成本、归集到用户 |

## 二、整体架构

### 2.1 逻辑分层

```
┌────────────────────────────────────────────────┐
│  Layer 1：客户端层（微信小程序原生）             │
│  - UI 渲染、用户输入、本地缓存、3D 渲染         │
└────────────────────┬───────────────────────────┘
                     │ HTTPS
┌────────────────────▼───────────────────────────┐
│  Layer 2：接入层（Caddy 网关）                  │
│  - TLS 终止、限流、鉴权透传、灰度路由          │
└────────────────────┬───────────────────────────┘
                     │
┌────────────────────▼───────────────────────────┐
│  Layer 3：业务服务层（NestJS 单体）             │
│  - 用户/宠物/订单/会员/作品/社交/工具          │
│  - 同步 API + 异步任务下发                      │
└────────────────────┬───────────────────────────┘
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
┌─────────────┐ ┌─────────┐ ┌─────────────┐
│ AI 网关层    │ │ 数据层  │ │ 外部服务层  │
│ (Python)    │ │(MySQL/  │ │(微信/AI/OSS)│
│ 任务编排    │ │ Redis)  │ │             │
│ Prompt 管理 │ │         │ │             │
│ 限流降级    │ │         │ │             │
└─────────────┘ └─────────┘ └─────────────┘
```

### 2.2 数据流向（按场景）

**同步请求（如登录、查询）**：
```
小程序 → Caddy → 业务服务 → MySQL/Redis → 返回
耗时目标：P99 < 500ms
```

**异步请求（如 AI 生成）**：
```
小程序 → 业务服务 → 校验额度 → 入库 ai_tasks → 入队 BullMQ
     ← 返回 task_id
                              ↓
AI 网关 Worker ← BullMQ
     → 调用第三方 AI
     → 接收 Webhook
     → 下载结果到 OSS
     → 更新 ai_tasks.status = success
     → 通知业务服务
                                    ↓
小程序轮询 /v1/ai/tasks/{id} ← 业务服务 ←
```

## 三、技术栈选型（决策记录）

### 3.1 客户端

| 候选 | 优势 | 劣势 | 决策 | 依据 |
|------|------|------|------|------|
| 微信原生小程序 | 启动快、API 完整、支付无缝 | 跨端能力差 | ✅ **采用** | 主战场是微信 |
| Taro | 一码多端 | 学习成本、3D 库生态差 | ❌ 暂不采用 | 收益 < 成本 |
| Uni-app | 生态成熟 | 性能损耗 | ❌ 暂不采用 | 同上 |

**组件库**：

| 候选 | 评估维度 | 决策 |
|------|---------|------|
| TDesign Miniprogram | 腾讯出品、组件齐全、企业级视觉 | ⭐⭐⭐⭐⭐ 备选 |
| Vant Weite | 社区活跃、移动端经验丰富 | ⭐⭐⭐⭐ 备选 |
| 自研 | 完全可控 | ❌ 投入大 |

> **待实测**：需做视觉 Demo 对比后定。

**3D 渲染**：
- 唯一可用方案：`three.js-miniprogram`（微信适配版）
- 不存在备选。需关注微信更新兼容性

### 3.2 后端框架

| 候选 | 优势 | 劣势 | 决策 | 依据 |
|------|------|------|------|------|
| NestJS | TypeScript、模块化、生态成熟 | 学习曲线 | ✅ **采用** | 长期可维护 |
| Express | 极简、灵活 | 缺少规范 | ❌ | 独立开发者需要约束 |
| Egg.js | 阿里系、企业实践多 | 社区活跃度下降 | ❌ | 选新不选旧 |
| Fastify | 性能好 | 生态较小 | ❌ | 与 NestJS 性能差距 < 30% |

**为什么 NestJS**：
1. 强制模块化 → 单体演进为微服务的路径清晰
2. 内置 Swagger → 自动生成 API 文档
3. TypeScript → 类型安全
4. 生态完善 → 微信支付、Redis、TypeORM 都有官方模块

### 3.3 AI 网关语言

| 候选 | 优势 | 决策 |
|------|------|------|
| Python (FastAPI) | AI 生态成熟、SDK 丰富 | ✅ **采用** |
| Node.js | 统一技术栈 | ❌ 备选 |
| Go | 性能 | ❌ 投入大 |

**为什么 Python**：
- 各 AI 服务商官方 SDK 都是 Python 优先
- Prompt 调试工具链成熟（LangChain、PromptTools）
- 与主业务隔离，互不影响

### 3.4 数据库

| 候选 | 适用 | 决策 |
|------|------|------|
| MySQL | 主业务数据、关系强 | ✅ **采用** |
| PostgreSQL | 复杂查询、地理信息 | ❌ 备选 |
| MongoDB | 文档型、JSON 自由 | ❌ 与业务不匹配 |

**为什么 MySQL**：
- 团队熟悉度高
- 运维工具链成熟（备份、监控、迁移）
- JSON 字段也能应对灵活业务

### 3.5 缓存与队列

| 用途 | 选型 | 理由 |
|------|------|------|
| 缓存 | Redis 7 | 标配 |
| 异步队列 | BullMQ (Redis) | 简单、轻量、与 NestJS 无缝集成 |
| 实时推送 | WebSocket（自建） | MVP 期不上专业推送服务 |

## 五、部署架构

### 5.1 MVP 期（单机）

```
┌──────────────────────────────────────────┐
│  云服务器（配置待实测，根据并发调整）      │
│  ┌────────────────────────────────────┐ │
│  │  Docker Compose                    │ │
│  │  - api (NestJS)         :3000      │ │
│  │  - ai-gateway (Python)  :8000      │ │
│  │  - mysql                :3306      │ │
│  │  - redis                :6379      │ │
│  │  - caddy                :80/443    │ │
│  └────────────────────────────────────┘ │
└──────────────────────────────────────────┘
         │              │
         ▼              ▼
     阿里云 OSS       微信开放平台
     (文件存储)       (支付/订阅)
```

**资源估算公式**（待实测修正）：

```
API 服务：核心数 = ceil(日活 × 单用户每日 API 数 × 平均 RT / 86_400_000 × 安全系数 3)
AI 网关：核心数 = ceil(日生成任务数 × 平均生成时长 / 86_400_000 × 安全系数 5)
MySQL：内存 = 数据量 GB × 0.3（建议 ≥ 2GB）
Redis：内存 = 缓存 key 数 × 平均 value size × 1.5

参考初值（待实测）：
- 日活 1000、单用户日均 5 次 API、平均 RT 200ms
  → API 核心数 ≈ ceil(1000 × 5 × 0.2 / 86400 × 3) ≈ 0.035 核（极小）
- 日任务 500、生成 30s
  → AI 网关核心数 ≈ ceil(500 × 30 / 86400 × 5) ≈ 0.87 核（基本满足）

但实际需考虑：
- AI 网关 Worker 是 IO 密集型，不是 CPU 密集
- 突发流量 = 平均流量 × 5-10
- 操作系统 + Docker 占基础 1-2 核
```

**结论**：MVP 期 4 核 8G 是**合理起点**，但需预留弹性。

### 5.2 进阶期（业务上涨后）

**触发条件**：日活 > 5000 或 AI 任务 > 2000/日 或 P99 延迟 > 3s

**改造路径**（按优先级）：

1. **MySQL 主从**（读写分离）—— 解决读瓶颈
2. **AI 网关独立部署** —— 让 API 服务不被 AI 任务阻塞
3. **OSS + CDN 升级** —— 图片加载性能
4. **多 ECS + SLB** —— 单点故障兜底
5. **拆微服务** —— 团队 > 3 人时再考虑

### 5.3 部署流程

```
本地开发
    ↓ git push
GitHub
    ↓ webhook
GitHub Actions
    ├─ Lint + Type Check + Test
    ├─ Docker Build (按服务拆镜像)
    └─ SSH 到 ECS
        ├─ 拉取镜像
        ├─ 蓝绿部署（保留旧容器）
        └─ 健康检查通过 → 下线旧容器
```

**回滚策略**：
- 镜像保留最近 10 个 tag
- 数据库迁移脚本必须有 `down` 方法
- 配置变更可热加载

## 六、AI 调用层

### 6.1 任务状态机

```
[pending] ──入队──> [pending]
    ↓ 调度
[processing] ──调用三方──> [processing]
    ↓ 完成回调
[success] ──入库结果──> [success]
    ↓ 失败回调
[failed] ──重试≤3──> [pending]
    ↓ 超过重试
[failed] ──通知用户──> [failed]

任意状态可转：
[cancelled] ──用户主动取消──> [cancelled]
```

### 6.2 限流策略

| 维度 | 阈值 | 实现 |
|------|------|------|
| 单用户并发任务数 | 2 | Redis INCR + TTL |
| 单用户每日任务数 | 免费额度 + 会员额度 | Redis 计数 |
| 全局并发任务数 | 待实测 | Redis 全局计数 |
| 单服务商 QPS | 依服务商限制 | 令牌桶 |

### 6.3 熔断与降级

**熔断规则**（按服务商）：
- 连续失败 5 次 → 熔断
- 熔断时长 60s
- 半开探测 → 通过 → 关闭；失败 → 重置熔断

**降级矩阵**（需确定主备方案后再固化）：

| 主用 | 备用 | 触发条件 |
|------|------|---------|
| 大语言模型 A | 大语言模型 B | 失败率 > 30% |
| 图生图 A | 图生图 B | 失败率 > 30% |
| 3D 生成 A | 3D 生成 B | 失败率 > 30% |

> **待实测**：需先确定各家备用，再写入配置。

### 6.4 成本归集

每次 AI 调用必须记录：
- `task_id`
- `provider`
- `model`
- `input_tokens` / `output_tokens` / `image_count` / `duration_seconds`
- `cost_cents`（按服务商实际计费换算）

成本归集公式（按用户）：
```
用户月度成本 = Σ(该用户所有 ai_tasks.cost_cents)
```

用于：
- 监控 ARPU / 成本比
- 异常用户预警（成本 > 收入）
- 服务商比价

## 七、缓存设计

### 7.1 缓存分类

| 类别 | 用途 | TTL |
|------|------|-----|
| 会话 | JWT 验证 | Token 有效期 |
| 业务快照 | 会员权益、用户额度 | 1h-1d |
| 静态数据 | 品种库、模板库、风格库 | 1h-24h |
| 限流计数 | 各类 counter | 1s-1d |
| 分布式锁 | 幂等控制 | 任务执行时长 |

### 7.2 缓存更新策略

| 场景 | 策略 |
|------|------|
| 用户主动行为触发 | 先更新 DB，再删缓存 |
| 后台定时任务 | 双写 + 异步刷新 |
| 静态数据变更 | 主动失效 + 版本号 |

### 7.3 缓存穿透 / 击穿 / 雪崩

| 问题 | 应对 |
|------|------|
| 穿透 | 空值缓存 + 布隆过滤器 |
| 击穿 | 互斥锁 / 逻辑过期 |
| 雪崩 | 随机 TTL + 多级缓存 |

## 八、安全设计

### 8.1 传输与存储

- 全站 HTTPS（TLS 1.2+）
- 敏感字段 AES-256 加密（过敏史、症状描述等）
- 数据库连接 SSL
- OSS 私有读 + 签名 URL

### 8.2 接口安全

| 措施 | 说明 |
|------|------|
| JWT | 7 天有效 + Refresh 30 天 |
| 签名 | 敏感接口加 HMAC 签名（防重放）|
| 限流 | IP + 用户双维度 |
| 输入校验 | class-validator 严格模式 |
| 输出转义 | 防止 XSS |
| SQL 注入 | ORM 参数化查询 |

### 8.3 内容安全

| 层级 | 措施 |
|------|------|
| 用户输入 | 关键词过滤 + 内容安全 API |
| AI 输出 | 强制审核后才展示 |
| UGC | 机审 + 抽检人工 |

## 十、技术决策记录（ADR）

### ADR-001：选择 NestJS 而非 Egg.js

- **背景**：需要选择一个 Node.js 后端框架
- **决策**：使用 NestJS
- **理由**：模块化清晰、TypeScript 强类型、生态活跃、自动 Swagger
- **代价**：学习曲线相对陡
- **替代方案**：Egg.js（阿里系，社区活跃度下降）；Express（缺少规范）

### ADR-002：AI 网关用 Python 独立进程

- **背景**：AI 调用是否与业务服务同进程
- **决策**：AI 网关独立 Python 进程
- **理由**：
  1. AI SDK 生态主要在 Python
  2. AI 任务长耗时不阻塞主 API
  3. 独立扩容方便
- **代价**：多一套部署、跨语言调用
- **状态**：决策保留，**待 P1 阶段实施**

### ADR-003：MVP 不上 K8s

- **背景**：是否一开始就容器编排
- **决策**：MVP 用 Docker Compose
- **理由**：单台机器、1-2 人运维，K8s 复杂度远超收益
- **触发升级**：日活 > 1 万 或 团队 > 3 人

### ADR-004：数据库先用 MySQL 单库

- **背景**：是否一开始分库分表
- **决策**：MySQL 单库
- **理由**：初期数据量 < 100 万行，分库成本高、收益小
- **触发升级**：单表 > 500 万行

### ADR-005：AI 服务商待实测后选型

- **背景**：是否提前锁定 AI 服务商
- **决策**：暂列候选、待 P0 阶段实测
- **理由**：各服务商价格、效果、稳定性都在变化，**过早锁定制约后期**
- **行动项**：P0 阶段对每个能力测试 ≥ 2 家服务商

### ADR-006：实时推送先用 WebSocket 自建

- **背景**：是否引入专业推送服务
- **决策**：MVP 用 WebSocket 自建
- **理由**：初期用户量小、推送频次低
- **触发升级**：DAU > 5000 或推送延迟 > 1s

## 十一、容量规划（公式化）

### 11.1 用户容量

```
单实例 API 服务可支撑用户数 = (核心数 × 86400 × 1000) / (单用户日均 API × P99 RT)
```

例：4 核、P99 200ms、单用户日均 10 次：
= (4 × 86400 × 1000) / (10 × 200)
≈ 172,800 用户

但实际需考虑：
- 平均 QPS ≠ 峰值 QPS（峰值 = 平均 × 5-10）
- 数据库连接池上限
- 长任务占用

### 11.2 存储容量

```
用户图片存储 = DAU × 上传率 × 平均 size × 保留天数
OSS 月成本 = 存储 GB × 0.12 + 流量 GB × 0.5
```

例：DAU 1000、上传率 50%、平均 2MB、保留 90 天：
= 1000 × 0.5 × 2 × 90 ≈ 90GB
月成本 ≈ 90 × 0.12 + 流量 ≈ ~30 元 + 流量

### 11.3 成本估算

> **所有数字均为示例，实际需实测**

| 项目 | 公式 | 备注 |
|------|------|------|
| 服务器 | 配置 × 云厂商报价 | 见 §5.1 |
| API 调用 | 调用次数 × 单价 | 各服务商报价不同，需实测 |
| 存储 | 数据量 × 0.12 元/GB | 见 §11.2 |
| 流量 | 流量 GB × 0.5 元 | 国内 CDN |

## 十二、演进路线

```
MVP（当前）
├ 单机 Docker Compose
├ 单库 MySQL
├ 单 Redis
├ 同步 + 异步混合 API
└ 人工运营

       ↓ 触发条件：DAU > 5000 或延迟 > 3s

成长（3-6 个月）
├ MySQL 主从
├ AI 网关独立部署
├ 引入 CDN
├ 引入 APM
└ 半自动运营

       ↓ 触发条件：DAU > 5 万 或团队 > 3 人

成熟（6-12 个月）
├ 多 ECS + SLB
├ 分库分表
├ Redis Cluster
├ 拆微服务（按业务域）
└ 全自动运营 + AI 辅助

       ↓ 触发条件：DAU > 50 万

规模化（12+ 月）
├ K8s 容器编排
├ 多区域部署
├ 大数据平台
└ 专业化运维团队
```
