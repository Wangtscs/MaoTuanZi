# 毛团子AI · 任务拆解与 Issue 模板

**版本**：V1.0 | **更新日期**：2026-08-18

> 本文档定义任务粒度、GitHub Issue 模板与标签体系。**面向小团队（1-3 人）**，规则务实可执行。

---

## 一、任务粒度

### 1.1 原则

| 维度 | 规则 |
|------|------|
| 单任务工作量 | ≤ 1 人日 |
| 单 PR 变更 | ≤ 300 行 |
| 任务可独立验收 | 必须有明确验收标准 |
| 任务可独立发布 | 不阻塞其他任务 |

### 1.2 任务来源

| 来源 | 优先级 | 例子 |
|------|:---:|------|
| PRD 功能 | P0 | 用户登录、AI 画像生成 |
| Bug 修复 | 按严重程度 | 支付回调失败 |
| 技术债 | P2 | 重构某个模块 |
| 优化 | P3 | 性能优化、代码规范 |

## 二、GitHub Issue 模板

### 2.1 Feature（功能）模板

创建文件 `.github/ISSUE_TEMPLATE/feature.md`：

```markdown
---
name: 功能请求
about: 申请新功能
title: '[Feature] '
labels: ''
assignees: ''
---

## 需求背景

（为什么需要这个功能？解决什么问题？）

## 用户故事

作为 [用户角色]，我想要 [功能]，以便 [价值]

## 验收标准

- [ ] 条件 1
- [ ] 条件 2
- [ ] 条件 3

## 设计稿 / 原型

（如有，附图或链接）

## 关联

- PRD 章节：
- 关联 Issue：

## 优先级

- [ ] P0（必做）
- [ ] P1（核心）
- [ ] P2（一般）
- [ ] P3（可选）

## 工期估算

预估人日：
```

### 2.2 Bug 模板

创建文件 `.github/ISSUE_TEMPLATE/bug.md`：

```markdown
---
name: Bug 报告
about: 报告一个 Bug
title: '[Bug] '
labels: 'bug'
assignees: ''
---

## 描述

（清晰描述 Bug）

## 复现步骤

1. 步骤 1
2. 步骤 2
3. 步骤 3

## 预期 vs 实际

- **预期**：xxx
- **实际**：xxx

## 截图 / 录屏

（必要附件）

## 环境

- 客户端版本：
- 微信版本：
- 系统：

## 优先级

- [ ] P0（生产不可用）
- [ ] P1（核心功能受影响）
- [ ] P2（非核心功能）
- [ ] P3（体验问题）

## 影响范围

- 受影响用户：xxx
- 业务影响：xxx
```

## 五、工作流

### 5.1 Issue 生命周期

```
Backlog → Todo → In Progress → In Review → Done
                                       ↓
                                    Blocked
```

### 5.2 看板视图

| 状态 | 说明 |
|------|------|
| **Backlog** | 待评估 |
| **Todo** | 已评估、待开始 |
| **In Progress** | 进行中（同时最多 2 个）|
| **In Review** | PR 已开 / 待验证 |
| **Blocked** | 被阻塞 |
| **Done** | 已合并 / 已发布 |

### 5.3 周节奏

| 时间 | 内容 |
|------|------|
| 周一 | 周计划（从 Backlog → Todo） |
| 周二 | 开发启动 |
| 周三 | 中期检查 |
| 周四 | PR 集中 Review |
| 周五 | 周复盘 + 下周准备 |

## 六、PR 模板

创建文件 `.github/PULL_REQUEST_TEMPLATE.md`：

```markdown
## 变更类型

- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档
- [ ] 性能优化

## 变更内容

（简述做了什么 + 为什么）

Closes #xxx

## 测试

- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 本地手测通过

## 截图 / 录屏

（关键页面截图）

## Checklist

- [ ] 代码通过 lint
- [ ] TypeScript 类型检查通过
- [ ] 已更新相关文档
- [ ] 数据库迁移脚本已就绪
- [ ] 监控已配置
```

## 七、估算方法

### 7.1 T-Shirt 估算

| 等级 | 人日 |
|------|------|
| XS | 0.25 |
| S | 0.5 |
| M | 1 |
| L | 2 |
| XL | 3（需拆分） |
| XXL | 5+（必须拆分） |

### 7.2 拆分原则

| 信号 | 动作 |
|------|------|
| 估算 > L | 强制拆分 |
| 涉及多个模块 | 按模块拆 |
| 涉及前端 + 后端 | 按端拆 |
| 涉及数据库迁移 | 拆为单独任务 |

## 八、Sprint 节奏

### 8.1 Sprint 长度

**2 周**（10 个工作日）

### 8.2 Sprint 内容

| 类型 | 占比 |
|------|------|
| 计划任务 | 70% |
| Bug 修复 | 20% |
| 技术债 / 改进 | 10% |

### 8.3 容量

每人每 Sprint：

- **小团队（1-3 人）**：8-12 个任务点
- 预留 20% buffer

---

## 九、Daily Standup

### 9.1 形式

async 方式（微信群），每日 9:30 前发出：

```
昨天：
- 完成 xxx
- 提交 PR #xxx

今天：
- 进行 xxx
- 解决 yyy

阻塞：
- （无 / xxx）
```

### 9.2 同步会议

需要时拉 15 分钟同步会议。

---

## 十、回顾机制

### 10.1 Sprint Review

每个 Sprint 结束：

- 演示完成的功能
- 数据回顾（按 15-埋点）
- 调整下个 Sprint

### 10.2 季度复盘

- 目标完成情况
- 关键决策回顾
- 下季度 OKR
