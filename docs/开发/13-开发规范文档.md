# 毛团子AI · 开发规范文档

**版本**：V2.0 | **更新日期**：2026-08-18

> 本文档是编码、Git 协作、测试的标准。**面向 1-2 人小团队**，规则务实可执行，不照搬大厂流程。

---

## 一、Git 规范

### 1.1 分支策略（简化 Git Flow）

```
main（生产）
  │
  ├── develop（集成分支，默认）
  │    ├── feature/xxx（功能）
  │    ├── fix/xxx（修复）
  │    ├── refactor/xxx（重构）
  │    ├── docs/xxx（文档）
  │    └── perf/xxx（性能）
  │
  └── hotfix/xxx（紧急修复 → main + 合并回 develop）
```

| 分支 | 命名 | 用途 |
|------|------|------|
| main | main | 生产代码，Tag 标记版本 |
| develop | develop | 集成最新功能 |
| feature/ | feature/portrait-style | 单个功能 |
| fix/ | fix/payment-timeout | bug 修复 |
| hotfix/ | hotfix/login-fail | 生产紧急修复 |
| docs/ | docs/update-readme | 文档 |

### 1.2 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>（不超过 50 字）

<body>（可选，说明动机）

<footer>（可选，关联 Issue）
```

**type 类型**：

| type | 含义 |
|------|------|
| feat | 新功能 |
| fix | bug 修复 |
| docs | 文档 |
| style | 代码格式（无逻辑变更）|
| refactor | 重构（无功能变更）|
| perf | 性能优化 |
| test | 测试 |
| chore | 构建 / 工具 / 依赖 |
| revert | 回退 |

**scope 范围**（按模块）：

`user` / `pet` / `ai` / `work` / `order` / `vip` / `tool` / `square` / `system` / `infra` / `deps`

**示例**：

```
feat(ai): 新增 3D 数字手办快速模式

- 支持单图生成 3D 模型
- 集成 Tripo3D API

Closes #123
```

### 1.3 提交频率

- 单次提交 ≤ 300 行变更（不含 lock 文件）
- 一个 feature 拆成多次提交
- 每次提交**可独立运行 / 编译**

### 1.4 PR / Merge 规范

**PR 标题**：同提交格式

**PR 描述模板**：

```markdown
## 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档

## 变更内容
（简述做了什么 + 为什么）

## 关联
Closes #xxx

## Checklist
- [ ] 代码通过 lint
- [ ] 已添加 / 更新测试
- [ ] 已更新相关文档
- [ ] 本地手测通过
```

**合并策略**：

| 场景 | 策略 |
|------|------|
| feature → develop | Squash Merge（保持历史整洁）|
| develop → main | Merge Commit（保留集成历史）|
| hotfix → main | Squash + 同步到 develop |

**Tag**：

```
v1.0.0    # 首发
v1.1.0    # 新增 3D 模块
v1.1.1    # Bug 修复
```

### 1.5 Code Review

> **小团队务实版**：独立开发者可自 Review，重点关注设计而非形式。

**什么时候必须有人 Review**：
- 涉及核心业务（订单、支付、AI 任务）
- 涉及数据迁移
- 涉及公共组件 / 工具函数
- 涉及安全相关

**Review 关注点**（优先级排序）：

1. **逻辑正确性**：边界条件、异常处理
2. **安全性**：SQL 注入、XSS、权限校验
3. **可维护性**：命名清晰、无重复代码
4. **性能**：N+1 查询、缓存缺失
5. **测试**：核心路径有测试

**Review 时间**：24 小时内响应（独立开发者 = 自己处理）。

## 二、代码规范

### 2.1 通用原则

| 原则 | 含义 |
|------|------|
| KISS | 保持简单，不要过度设计 |
| DRY | 不重复代码 |
| YAGNI | 不写暂时不需要的代码 |
| SRP | 一个函数 / 类只做一件事 |
| 显式优于隐式 | 避免魔法值、魔法字符串 |

### 2.2 TypeScript / JavaScript

**配置**：
- `tsconfig.json` 启用 `strict: true`
- 禁用隐式 `any`
- 必要 `any` 用 `unknown` + 类型守卫

**命名规范**：

| 类型 | 规范 | 示例 |
|------|------|------|
| 变量 | camelCase | `userName` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 函数 | camelCase + 动词 | `getUserById` |
| 类 | PascalCase | `UserService` |
| 接口 | PascalCase | `IUserService` 或 `UserService` |
| 类型 | PascalCase | `UserRole` |
| 枚举 | PascalCase + PascalCase 成员 | `OrderStatus.Pending` |
| 文件 | kebab-case | `user-service.ts` |
| 组件 | PascalCase | `UserCard.tsx` |

**格式化**：
- Prettier：2 空格缩进、单引号、无分号（项目统一）
- ESLint + Airbnb 规则 + 自定义规则

**注释**：

```typescript
/**
 * 根据宠物档案生成 AI 画像任务
 * @param petId 宠物 ID
 * @param style 风格标识
 * @returns 任务 ID（异步任务）
 */
async function generatePortrait(petId: number, style: string): Promise<string> {
  // 实现
}
```

**TODO 格式**：`// TODO(username): 内容`

### 2.3 Python

- 遵循 PEP 8
- Black 格式化
- Flake8 + MyPy

| 类型 | 规范 |
|------|------|
| 变量 / 函数 | snake_case |
| 类 | PascalCase |
| 常量 | UPPER_SNAKE_CASE |
| 文件 | snake_case |

### 2.4 数据库

- 全部小写 + 下划线（`user_id` 而非 `userId`）
- 表名复数（`users` 而非 `user`）
- 字段名单数
- 主键统一 `id`
- 时间字段 `created_at` / `updated_at`
- 软删除统一 `deleted_at`（DATETIME，**禁止混用 `is_deleted`**）
- 金额字段 `xxx_cents`（整数分）

> 与设计-05 数据库设计文档一致。

### 2.5 API 接口

- RESTful，URL 复数
- 资源名词，动作用 POST
- 返回统一格式（与设计-06 一致）

### 2.6 错误处理

```typescript
// ✅ 推荐：自定义错误类
class BusinessError extends Error {
  constructor(public code: number, message: string) {
    super(message);
  }
}

// ❌ 避免：吞掉错误
try {
  await doSomething();
} catch (e) {
  // 静默
}
```

**日志输出**（结构化）：

```typescript
logger.error('ai_task_failed', {
  task_id: 't_123',
  user_id: 456,
  error_msg: e.message,
  trace_id: ctx.traceId
});
```

## 三、测试规范

### 3.1 测试金字塔

```
       /\         E2E（少量，关键路径）
      /  \
     /----\
    /      \     集成测试（API 层）
   /--------\
  /          \   单元测试（业务逻辑）
 /────────────\
```

### 3.2 单元测试

- 框架：Jest（Node）/ pytest（Python）
- **目标覆盖率**：
  - 核心业务（订单、支付、AI 任务）≥ 70%
  - 工具函数 ≥ 80%
  - 辅助功能 ≥ 50%
- 测试命名：`test_<module>_<scenario>_<expected>`

**示例**：

```typescript
describe('UserService', () => {
  describe('getUserById', () => {
    it('should return user when id exists', async () => {
      // ...
    });

    it('should throw NotFoundError when id not exists', async () => {
      // ...
    });
  });
});
```

### 3.3 集成测试

- 测试 API 接口契约
- Supertest（Node）/ requests（Python）
- 每个 controller 至少 3 个用例（正常、异常、边界）

### 3.4 E2E 测试

- 关键路径：登录 → 创建宠物 → 生成画像 → 支付 → 查看作品
- 工具：微信小程序自动化（miniprogram-automator）
- 频率：上线前 + 重大变更后

### 3.5 测试数据

- 使用 Factory 模式生成测试数据
- 不使用生产数据
- 测试数据库独立

## 四、文档规范

### 4.1 代码内文档

- 公开 API 必须有 JSDoc
- 复杂业务逻辑必须有注释
- TODO 必须有 owner 和说明

### 4.2 架构文档

- 任何架构变更必须更新对应设计文档
- 新增模块必须在 `docs/` 下创建文档
- 每月一次架构 review

### 4.3 README

每个子项目必须有 README：

```
项目名
├── 简介（做什么）
├── 技术栈
├── 目录结构
├── 本地启动
├── 部署
├── 测试
└── License
```

## 五、依赖管理

### 5.1 添加依赖原则

| 维度 | 规则 |
|------|------|
| 成熟度 | 优先选成熟、活跃维护的库 |
| 必要性 | 避免不必要的依赖（能用原生就用原生）|
| 引入前评估 | 包大小、维护活跃度、License |
| 定期清理 | 每季度 review 一次 |

### 5.2 版本控制

- 提交 `package-lock.json` / `yarn.lock` / `poetry.lock`
- 使用语义化版本范围（`^1.2.3`）
- 升级前必须测试

### 5.3 安全审计

- 每月运行 `npm audit` / `pip-audit`
- 高危漏洞 **24 小时内** 修复
- 中危漏洞 **7 天内** 修复

## 六、环境管理

### 6.1 三环境

| 环境 | 用途 | 数据 |
|------|------|------|
| dev | 本地开发 | 测试数据 |
| staging | 预发布 | 仿真数据 |
| prod | 生产 | 真实数据 |

### 6.2 配置管理

- 配置文件分离：`.env.development` / `.env.production`
- **禁止** 把密钥提交到 Git
- 使用 `.env.example` 提交模板
- 生产密钥使用密钥管理服务（阿里云 KMS）

## 七、发布规范

### 7.1 发布流程

```
feature → develop → staging 测试 → main → tag → 灰度 → 全量
```

### 7.2 版本号

遵循 **语义化版本** `MAJOR.MINOR.PATCH`：

- **MAJOR**：不兼容的 API 变更
- **MINOR**：向后兼容的功能新增
- **PATCH**：向后兼容的 bug 修复

### 7.3 发布前 Checklist

- [ ] 所有测试通过
- [ ] 代码覆盖率达标
- [ ] 文档已更新
- [ ] 配置文件正确
- [ ] 数据库迁移脚本就绪
- [ ] 监控 / 告警配置
- [ ] 回滚方案就绪

## 八、监控与日志

### 8.1 日志级别

| 级别 | 用途 |
|------|------|
| ERROR | 错误事件，需要关注 |
| WARN | 警告，可能有问题 |
| INFO | 关键业务流程 |
| DEBUG | 调试用，prod 关闭 |

### 8.2 日志格式（JSON）

```json
{
  "timestamp": "2026-08-18T10:00:00Z",
  "level": "INFO",
  "trace_id": "abc123",
  "user_id": 456,
  "module": "ai_task",
  "message": "task created",
  "data": {
    "task_id": "t_789",
    "type": "portrait_2d"
  }
}
```

### 8.3 关键监控点

| 监控点 | 指标 |
|--------|------|
| API 入口 | QPS、延迟、错误率 |
| AI 任务 | 创建数、成功率、平均耗时 |
| 数据库 | 连接数、慢查询 |
| 缓存 | 命中率、内存使用 |
